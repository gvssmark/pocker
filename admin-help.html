Family Hold'em

Administrator Guide

For whoever manages the Firebase project and the approved-hosts list. This assumes the app is already deployed — see the main README for first-time setup.

Adding a new approved host email

This is the step most likely to go wrong, so follow it exactly. Only emails on this list can create a table (anyone can still join one with a room code, unrestricted).

The #1 mistake: importing at the wrong location. "Import JSON" replaces everything at whatever path you're currently viewing — do this at the database root and you will wipe your entire database, not just the email list.
  1. 1Go directly to this exact URL (edit in your project name if different): 
    https://console.firebase.google.com/project/YOUR-PROJECT/database/YOUR-PROJECT-default-rtdb/data/allowedEmails
    Confirm the page says "This location does not have any data" (if it's empty) or shows your existing list — either way, confirm allowedEmails appears in the breadcrumb at the top, not just data/.
  2. 2Click the ⋮ menu near the top of that panel → Import JSON.
  3. 3Paste a flat object — every "." in the email becomes a ",", and everything should be lowercase: 
    {
  "jane,smith@gmail,com": true,
  "raj,kumar@outlook,com": true
}
    Firebase database keys can't contain a literal dot, which is why this conversion is necessary. The app does this same conversion automatically when checking who signed in — so as long as the stored key matches this pattern, it'll match correctly.
  4. 4Click Import.
  5. 5Verify it landed correctly: click into one of the new entries and check the URL bar reads .../data/allowedEmails/jane,smith@gmail,com — with allowedEmails visible in the path. If instead you see something like .../data/~2Fjane,smith@gmail,com (no allowedEmails in the path, and a ~2F), the import happened at the wrong level and needs to be deleted and redone — see "If you accidentally import at the root" below.

To add one email without touching the rest

Instead of a full Import, you can also just click the + next to allowedEmails in the data view, and add a single child: key = the sanitized email (dots → commas), value = true. Slower for a batch, but zero risk of overwriting anything.

If you accidentally import at the root

You'll see the stray email keys sitting as top-level nodes, siblings of rooms and private — and rooms/private will likely be gone (this only affects live game state, not anything permanent — nobody loses anything meaningful, any in-progress table just needs to be recreated). To recover:

  1. Delete each stray key sitting at the root individually.
  2. Navigate precisely to .../data/allowedEmails again, confirm it's empty, and redo the import there.

Removing a host's access

Navigate to the specific entry under allowedEmails and delete just that node. It only affects their ability to create new tables going forward — it doesn't remove them from any table they're already part of.

Recommended hosting workflow (getting around the iOS sign-in restriction)

Creating a table requires Google sign-in, and Google flatly refuses to run that inside iOS's "Add to Home Screen" mode — an Apple/Google platform restriction with no code-level fix. The clean workaround, which the app fully supports:

  1. Whoever's on the approved list opens the link in regular Safari/Chrome, signs in, and creates the table under any name — a throwaway like "Table" is fine, since this identity's only job is getting the table started.
  2. That same person separately opens the home-screen icon and joins the same room with their real name — joining never needs sign-in, so this works fine from the home-screen app.
  3. Back in the browser tab, they tap their real-name entry in the player list (a direct tap on the name — underlined once there are 2+ players) and confirm, transferring hosting duties to the home-screen-app identity.

After the transfer, the placeholder identity is fully disposable — it's automatically put on a break (excluded from all future hands, hidden from the table view, chips untouched but irrelevant), and the browser tab can be closed entirely. The game keeps running normally on whichever device now holds hosting duties; nothing about the transferred-to device depended on that original tab staying open.

Transfer only works between hands — never mid-hand, since the shuffled deck lives only in the current host's device memory and genuinely can't be handed off while a hand is live.

Rules changes

Whenever you edit database.rules.json in the repo, you still need to manually paste the updated content into Realtime Database → Rules tab in the Firebase console and click Publish — pushing to GitHub only updates the app files, not the live rules.

Troubleshooting a stuck "Dealing…" screen

The host's device — whoever created the table — holds the shuffled deck only in that browser tab's memory, by design (that's what keeps it private). If that tab reloads or loses connection mid-hand, the game can't continue automatically.

What to do: the host should see a "Redeal this hand" button appear automatically in this situation. Tapping it deals a fresh hand with the same players and blinds — no chips are lost or duplicated, since bets aren't committed to anyone's total until a hand fully finishes.

If it happens and you're not sure why: open the menu → Copy debug log on the device it happened on (usually the host's) and send that to whoever's maintaining the app — it traces every step from that hand's deal through to wherever it got stuck.

If updates to the app don't seem to take effect

The app installs a small offline cache (for the "Add to Home Screen" experience). It's set to always prefer the network when available, so a normal page reload should show the latest deployed version within a minute or two of pushing to GitHub. If something still looks stale: Settings → clear the site's data for this URL, or in desktop Chrome/Edge dev tools → Application tab → Service Workers → Unregister, then reload.

The host leaving ends the game

Whoever currently holds hosting duties leaving the table (via the menu) ends the game for everyone, with a confirmation shown first so it can't happen by accident. This is deliberate — this app has no server component to keep a game alive with nobody responsible for dealing, so a clean, obvious end beats a table quietly stuck forever. It only fires for the current host — after a transfer (see above), the outgoing host can leave freely without ending anything.

Everything here runs on Firebase's free Spark plan — no credit card, and this app's usage (a handful of family game nights) is a tiny fraction of the free quota.
